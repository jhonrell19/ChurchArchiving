# Smart Parish role and endpoint matrix

The authoritative, reproducible matrix is generated by:

```powershell
node scripts/phase8_role_matrix.cjs
node tests/test_phase8_roles.cjs
```

The generator extracts and evaluates the actual `isAllowed` function from
`src/app/api/backend/[...path]/route.ts`, rather than manually inventing permission labels.
It covers Main Admin (`ADMIN`), Burial Admin (`BURIAL_ADMIN`), and parishioner (`USER`).
**There is no separately stored `STAFF` role** in the Prisma schema. Supervisory duties
use `PARISH_SUPER_ADMIN_ID`. Do not present Church Staff as an already implemented separate role.

Key boundaries beyond the proxy matrix:

- Access to `/api/backend/files/*` is a *proxy allowance* only; the Flask endpoint
  checks whether the path belongs to an eligible active Mass, own released/paid certificate,
  or office-scoped document. A 200 from the proxy function alone does not authorize file bytes.
- Request and file IDs require Flask ownership checks. Do not grant access solely because
  an endpoint route is listed.
- Main Admin cannot access burial/land/ownership categories, cemetery endpoints or
  Burial Admin's scoped certificates.
- Burial Admin cannot access baptismal/confirmation/marriage archives, Mass admin
  routes or Main Admin's reports.
- Parishioners can request their own certificates, submit claims, and view approved
  public Mass content; cannot mutate archives or read another person's certificate.
- Explicitly designated supervisor-only operations still require checks inside
  their handler, not just `ADMIN` in the proxy.
- Staff onboarding as a fourth stored role needs an explicit migration and full
  endpoint review; it is **not** safe to add a literal role value without implementing it.

To prove full enforcement, run the offline tests AND log in using the three
test roles on an isolated clone. Check each link and a direct URL to a
foreign request and scan. Never treat source-level allowlist tests alone as a security audit.
